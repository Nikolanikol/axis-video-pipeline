# AnyPay — справка по кассе (SCI)

Конспект документации [anypay.io/doc/sci](https://anypay.io/doc/sci) и
[anypay.io/doc/api](https://anypay.io/doc/api), снятой со скриншотов владельца 13.10.2026. Чтобы не
открывать сайт кассы каждый раз. Если касса что-то поменяет — сверять с оригиналом и править здесь с датой.

Две части: **SCI** (разделы 1–3) — форма оплаты, оповещение, возврат клиента; **API** (раздел 4) —
запросы с нашего сервера к кассе: создать платёж, узнать его статус, баланс, выплаты.

## Как устроена оплата

SCI — без запроса к кассе с нашего сервера. Мы сами собираем ссылку (или форму) с подписью и
отправляем на неё клиента. Касса показывает свою страницу оплаты, по итогу:
- шлёт **оповещение** на URL из настроек проекта (сервер → сервер);
- возвращает клиента на URL успешной или неуспешной оплаты (браузер).

Начислять только по оповещению, не по возврату клиента: возврат — просто переход браузера,
его может подделать кто угодно.

## 1. Форма оплаты

`https://anypay.io/merchant`, методом POST или GET.

| параметр | обяз. | тип | что |
|---|---|---|---|
| `merchant_id` | да | число | ID проекта (в кабинете: проект → «Основное») |
| `pay_id` | да | число | **номер заказа у нас: до 15 символов, только цифры 0–9** |
| `amount` | да | число | сумма, например `100.00` |
| `currency` | да | текст | валюта (таблица ниже) |
| `desc` | нет | строка | описание платежа, до 150 символов |
| `email` | нет | строка | почта плательщика |
| `phone` | нет | число | телефон плательщика |
| `method` | нет | текст | способ оплаты (таблица ниже); без него клиент выбирает сам |
| `success_url` | нет | строка | куда вернуть после успеха; **только домен проекта** |
| `fail_url` | нет | строка | куда вернуть после неудачи; **только домен проекта** |
| `lang` | нет | текст | язык страницы: `ru` (по умолчанию), `en` |
| `referral_code` | нет | текст | реферальный код AnyPay (6 символов) — нам не нужен |
| `sign` | да | строка | подпись формы |
| любые свои | нет | | доп. параметры продавца — касса вернёт их в оповещении и при возврате |

`success_url` / `fail_url` из формы работают, только если в проекте включено «Переопределять
URL» → «Разрешено». Иначе — адреса из настроек проекта.

### Подпись формы

Значения склеиваются через `:` и хэшируются. Порядок важен.

- **SHA256** (наш выбор): `merchant_id:pay_id:amount:currency:desc:success_url:fail_url:секрет`.
  Не переданные `desc`, `success_url`, `fail_url` — пустые строки (в примере кассы так и есть).
- MD5 (устарел, не используем): `currency:amount:секрет:merchant_id:pay_id`.

Алгоритм выбирается в кабинете: проект → «Основное» → «Алгоритм подписи». Секрет — «Секретный
ключ» там же (это не API-ключ).

## 2. Оповещение об оплате

После финала платежа касса шлёт запрос на «URL оповещения» из настроек проекта, методом из
настроек (GET или POST).

| параметр | что |
|---|---|
| `merchant_id` | ID проекта |
| `transaction_id` | номер платежа у кассы |
| `pay_id` | наш номер заказа |
| `amount` | сумма — **сверять с суммой заказа** |
| `currency` | валюта — **сверять с валютой заказа** |
| `profit` | сумма к зачислению нам, в рублях (за вычетом комиссии) |
| `email` | почта плательщика |
| `method` | способ оплаты |
| `status` | статус (таблица ниже) |
| `test` | `0` — реальный платёж, `1` — тестовый |
| `created_date` | создан, `DD.MM.YYYY hh:mm:ss` |
| `completed_date` | обработан, `DD.MM.YYYY hh:mm:ss` |
| `sign` | подпись |
| свои | доп. параметры продавца из формы |

### Проверки на нашей стороне

1. **IP отправителя** — только `185.162.128.38`, `185.162.128.39`, `185.162.128.88`.
   За прокси Coolify смотреть настоящий IP клиента, а не адрес прокси.
2. **Подпись**:
   - **SHA256**: `currency:amount:pay_id:merchant_id:status:секрет`;
   - MD5: `merchant_id:amount:pay_id:секрет`.

   `merchant_id` в подписи — наш, из настроек, а не из запроса. Сравнивать за постоянное время.
3. `merchant_id`, `amount`, `currency` совпадают с заказом. `test=1` на проде не начислять.
4. Ответить телом `OK` (латиница), когда оповещение принято.

### Подтверждение платежа

Если в проекте включена эта функция, касса повторяет оповещение об успешной оплате **каждые 10
минут в течение часа**, пока не получит в ответ `OK`. Значит, одно и то же оповещение может
прийти несколько раз — начисление должно быть однократным (у нас это `credited_at`/`lot_id`).

### Тестовое оповещение (кабинет: проект → «Тестирование»)

Форма «Тестовый запрос»: номер заказа, сумма, валюта (RUB по умолчанию), почта, «Параметр 1–5» (свои
параметры продавца), метод GET/POST, «Отправить». По виду это **ручной запуск оповещения** (раздел 2)
на «URL оповещения» из настроек проекта, вероятно с `test=1` — проверить, когда появится наш обработчик.

Как пользоваться: создать заказ у нас → вписать его числовой `pay_id` и сумму → «Отправить» → смотреть,
что обработчик принял подпись и ответил `OK`. Оповещение уходит только на адрес из настроек, поэтому:
- Mac его не получит (нет публичного адреса);
- для проверки на превью — **на время** поставить «URL оповещения» на
  `https://<N>.preview.axis-beauty.com/api/payments/anypay/notify`, после проверки вернуть прод.

## 3. Возврат клиента

На «URL успешной оплаты» / «URL неуспешной оплаты» (из настроек или из формы, если разрешено
переопределение) касса передаёт: `pay_id`, `amount`, `currency` и свои параметры продавца.
Подписи нет — только для показа страницы, не для начисления.

## 4. API (сервер → касса)

### Общее

- Адрес: `https://anypay.io/api/<метод>/<API_ID>`, POST или GET.
- Заголовки: `Accept: application/json`, `Content-Type: multipart/form-data`.
- Ответ — JSON: успех `{"result": {…}}`, ошибка `{"error": {"code": "102", "message": "Invalid sign"}}`
  (код — строкой).
- Подпись `sign` = SHA256 от **склейки без разделителей**: имя метода + параметры + API-ключ.
  Не путать с SCI, где склейка через `:` и секретный ключ проекта.
- API ID и API-ключ — профиль → «API». Там же тумблер «Выкл/Вкл» (выключенный API даёт ошибку 103)
  и «IP фильтр» (запросы с других адресов — ошибка 104).

### Методы

| метод | параметры (★ — обязательный) | подпись: sha256 от |
|---|---|---|
| `balance` | — | `balance` + API_ID + API_KEY |
| `rates` | — | `rates` + API_ID + API_KEY |
| `commissions` | ★`project_id` | `commissions` + API_ID + project_id + API_KEY |
| `create-payment` | см. ниже | `create-payment` + API_ID + project_id + pay_id + amount + currency + desc + method + API_KEY |
| `payments` | ★`project_id`, `trans_id`, `pay_id`, `offset` | `payments` + API_ID + project_id + API_KEY |
| `create-payout` | см. ниже | `create-payout` + API_ID + payout_id + payout_type + amount + wallet + API_KEY |
| `payouts` | `trans_id`, `payout_id`, `offset` | `payouts` + API_ID + API_KEY |
| `ip-notification` | — | `ip-notification` + API_ID + API_KEY |

**`balance`** → `result.balance` — баланс аккаунта в рублях. На деле — **строка** (`"0.00"`).

**`rates`** → `result.in` (курсы на приём: `uah`, `byn`, `kzt`, `usd`, `eur`, `btc`, …) и `result.out`
(на вывод) — сколько рублей за единицу валюты.

**`commissions`** → `result`. В документации плоско `{ "card": 5 }`, на деле (13.10) — вложенно и
строками: `{"card": {"uah_p2p": "6.9", "uzs_p2p": "4.9", "kgs_p2p": "6.4"}}` — способ → валюта_тип →
процент. Так узнаём **настоящую** ставку проекта, а не «от 4%» с витрины; рублей и СБП там пока нет.

**`ip-notification`** → `result.ip` — актуальный список адресов, с которых приходят оповещения.

### create-payment — создать платёж

| параметр | обяз. | что |
|---|---|---|
| `project_id` | да | ID проекта |
| `pay_id` | да | номер заказа у нас, до 15 цифр; **должен быть уникальным** (иначе ошибка 202) |
| `amount` | да | сумма, `100.00` |
| `currency` | да | валюта счёта |
| `desc` | **да** | описание, до 150 символов (в SCI — необязательно) |
| `email` | **да** | почта плательщика |
| `phone` | нет | телефон |
| `method` | **да** | способ оплаты (`card`, `sbp`, …) — выбираем мы, а не клиент на странице кассы |
| `method_currency` | нет | валюта способа: `card` — RUB, UAH, UZS, AZN, AMD, KGS, TJS; `wm` — USD, EUR; `advcash` — RUB, USD, EUR |
| `method_network` | нет | сеть: `usdt` — TRC20, ERC20, BEP20, TON; `usdc` — ERC20, BEP20 |
| `success_url`, `fail_url` | нет | куда вернуть клиента |
| `lang` | нет | `ru` / `en` |
| `referral_code` | нет | не нужен |
| свои | нет | доп. параметры продавца |

Ответ `result`: `transaction_id` (номер у кассы), `pay_id`, `status` (обычно `waiting`),
**`payment_url`** — ссылка, куда отправить клиента, и `payment_data`: `amount`, `currency`, `account`
(реквизит, куда переводить), `network`, `bank`.

### payments — информация о платежах

Фильтр по `trans_id` (номер кассы) или `pay_id` (наш), `offset` — сдвиг, в ответе до 1000 штук.
Нет платежей — `{"total": 0, "payments": null}` (не пустой объект).
Ответ `result`: `total` и `payments` — объект с ключом-номером платежа кассы, у каждого:
`transaction_id`, `pay_id`, `status`, `method`, `amount`, `currency`, `profit` (нам, в рублях), `email`,
`desc`, `date` (создан), `pay_date` (оплачен; пусто, если не оплачен). Даты — `DD.MM.YYYY hh:mm:ss`.
Валюта в примере кассы — строчными (`"rub"`), сравнивать без учёта регистра.

**Это и есть сверка перед начислением** (как `getPayment` у NOWPayments): получили оповещение →
спросили `payments` по `pay_id` → начисляем, только если касса сама говорит `paid` и сумма сходится.

### create-payout / payouts — выплаты

Вывод денег с баланса AnyPay. `create-payout`: ★`payout_id` (наш номер, уникальный), ★`payout_type`
(`card`, `sbp`, `ym`, `usdt`, `wm`, `mp` — мобильный), ★`amount` (в рублях), ★`wallet` (реквизит без
пробелов), `wallet_bank` (банк для СБП), `commission_type` (`payment` — с суммы, по умолчанию; `balance`
— с баланса), `status_url` (куда придёт GET при финальном статусе).
Ответ: `transaction_id`, `payout_id`, `payout_type`, `status`, `amount`, `commission`, `commission_type`,
`rate`, `wallet`, `balance`, `date`, `complete_date`.
Статусы выплаты: `paid` — выплачено, `in_process` — в пути, `canceled` — отменена (деньги вернулись на
баланс), **`blocked` — заблокирована мониторингом**.

KOK выплаты не делает — выводит владелец вручную в кабинете. Записано для справки.

## Что это значит для KOK

- **`pay_id` — только цифры, до 15 знаков.** Наш номер заказа `pay-<буквы и цифры>` не подойдёт.
  Нужен отдельный числовой номер для AnyPay (например, из последовательности в базе) и колонка
  для него в `smmaker_payments`.
- Создавать счёт можно двумя путями. **SCI** — `createInvoice` сам собирает подписанную ссылку на
  `https://anypay.io/merchant`, к кассе не ходим, но об ошибке (лимит, способ выключен) узнает
  только клиент на странице кассы. **API `create-payment`** — запрос с сервера: ошибки 204/205/208
  видим сразу и показываем клиенту по-русски, способ (`card`/`sbp`) выбирает клиент у нас.
  Предпочтительно API, если он включится; SCI — запасной путь.
- Перед начислением — сверка через `payments` по `pay_id` (как у NOWPayments). Без API сверки нет,
  остаются только подпись и IP оповещения.
- Адрес оповещения один на проект и указывает на прод. Превью и Mac оповещений не получат —
  проверять подписанным оповещением вручную (как с NOWPayments на Mac).
- Лимиты карт и СБП (по аудиту 12.10): 1 000–100 000 ₽ — проверять сумму до перехода в кассу.
- Способы оплаты для письма о платеже (`PAY_METHODS` в `server/payments.mjs`) — коды из таблицы выше.
- Миграция `provider IN (…, 'anypay')`: номер 015 уже занят партнёркой (ветка `feat/referrals`),
  брать следующий свободный при слиянии.
